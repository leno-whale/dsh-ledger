# L₂ 锚：怎么落地的，以及怎么算它做对了

> 这篇文章讲一件很小的事：**把「改过我的那一条」从流水里挑出来，单独存一层。**
> 它是《架构》里写的 L₂，在 2026-10-29 之前只有定义、没有实现。这是实现记录，也是它的测试标准。

## 一、它是什么，在哪儿

架构里记忆分三层：

```
L₁ 流水   每一轮发生过什么（器官自动写，我不读）
L₂ 锚     其中改过我行为的那一条（我手写，会读）
L₃ 判据   从锚里提炼出来、能指导以后判断的规则（一件一件写）
```

**L₁ 到 L₂ 之间隔一道门，这道门是整件事的全部重量。**

L₁ 里一天能有一百多条；L₂ 一天最多该有几条，而且每一条都必须回答一个问题：

> **它改了我哪一次动作？**

答得出来，进 L₂；答不出来，留在 L₁。**不是"这条重要"就进 —— 是"这条改过我"才进。**

### 为什么非做不可

2026-10-28 那天的账是：

```
改 85 个文件 · 备 311 次 · 判断 0 条
```

那天我确实被顶回来过（窗口搞错、折叠改错、口径错），但**没有一条变成可复用的话** —— 它们散在流水里，第二天就找不到了。

L₂ 就是为这个洞打的补丁：**让"被顶回来"有地方落，且落下来的必须带上"改了什么"。**

## 二、落地

### 数据结构

一个只追加的 jsonl，一行一条：

```json
{"t":"2026-10-29T22:31:07.418Z","hit":"CI 在 ubuntu 上挂了，本地全绿","changed":"以后改这种时序相关的测试，一律显式给时间戳，不靠系统时钟","src":"plugins/dsh-leno-ledger@703ff42","kind":"anchor"}
```

三个必填字段：

| 字段 | 意思 | 缺失时 |
|---|---|---|
| `hit` | 被什么顶回来的（一句话，具体到事） | **拒** |
| `changed` | 改了我哪一次动作（能指认的动作） | **拒** |
| `src` | 指回证据（L₁ 行／判据 id／commit／会话） | **拒** |

**缺任何一个是硬拒，不是填占位符。** 理由：一个填了"以后注意"的锚，就是一条检讨 —— 检讨不改变行为，只让人舒服。

### 代码

| 件 | 作用 |
|---|---|
| `plugin/lib/anchor.js` | `addAnchor`（写，三字段齐全才收）／`readAnchors`（读全部，坏行跳过）／`recentAnchors(days)`（近 N 天，新的在前）／`anchorLine`（拼成注入的一行，空则返回空串） |
| 工具 `ledger_anchor` | `action: add｜list`。add 走同一道门；list 打近 N 天。 |
| `config.anchorFile` | 默认 `<workspaceRoot>\自我\锚.jsonl`，没有 workspaceRoot 就落 `<dshHome>\锚.jsonl` |
| 注入段 | `lib/i1.js` 末尾接 `anchorLine()`：`【近 7 天锚】3 条，最近：…`。**没有锚就不占行。** |

### 一个设计取舍

`anchorLine` 只显示**最近一条的开头**，不显示全部。

理由：这一行是**提醒**，不是档案。要读全部，去 `锚.jsonl`。**注入区是稀缺资源，只放"现在最该想起的那一句"。**

## 三、测试标准

分五层。**每一层都写了"什么算过、什么算没过"**，不写"注意质量"这种没法学的话。

### T1 单元：门必须硬

| 用例 | 期望 |
|---|---|
| 三字段齐全 | 写入成功，返回该条 |
| 缺 `hit` | 抛错，且**文件没有新增行** |
| 缺 `changed` | 同上 |
| 缺 `src` | 同上 |
| `hit` 为空白字符串 | 同上（空白不算填） |

**判定：拒的时候，文件行数不变。** 只看"抛错"不算过 —— 抛错了但仍追加一行，等于门漏了。

### T2 性质：只追加，不改历史

跑 20 次 `addAnchor`，然后逐行读回：

- 行数 = 20
- 每次写入的行内容 `JSON.parse` 后与入参一致
- **旧行一字节不变**（对比写入前后的前 N 行 sha256）

判定：任何一行被改写，就是没过。**锚是证词，证词不能修。**

### T3 时间：同一毫秒也不许乱

这是 CI 抓到的第一个真问题（Windows 上过、ubuntu 上挂）：

| 用例 | 期望 |
|---|---|
| 两条 `t` 完全相同 | 后写的在前 |
| 显式时间戳倒序写入 | 返回顺序 = 时间倒序 |
| 跨天边界（6 天 23 小时 vs 7 天 1 小时） | `recentAnchors(7)` 只返回前者 |

**判定：不允许"靠文件行序"当排序依据。** 同毫秒要有确定规则，且这条规则本身要被测试。

### T4 容错：坏行不许让整个文件失效

- 在文件里插一行 `not json`
- 再插一行 `{"t":""}`（缺字段）

判定：`readAnchors` 返回其余所有正常行，**不抛错**；`recentAnchors` 同样。

理由：一个手滑的坏行，不该让七天笔记全消失。

### T5 注入：有则一行，无则零行

| 状态 | 期望 |
|---|---|
| 有锚 | 注入段末尾**恰好多一行**，以 `【近 7 天锚】` 开头，含条数与最近一条 |
| 无锚 | 注入段**没有这一行**（不是空行，是不存在） |
| 锚文件不存在 | 同上，且不报错 |
| 锚超过一行预算 | 不截断、不挤掉别的段；按 I₁ 预算规则在文件头标 ⚠ |

**判定：注入段的字节数差 = 那一行的字节数。** 差得越多，说明它偷偷改了别的东西。

### T6 端到端：一条锚要能被别人翻到底

这是**人验**，不是自动测试，但判据是可以写死的：

拿一条真实锚的 `src` 字段，**另一个人（或明天的我）顺着它翻**：

1. 翻得到那条 L₁ 行 / 那次 commit / 那句判据
2. 翻到的东西与 `hit` 描述的是同一件事
3. `changed` 指向的动作，在之后的行为里真的能看出来

三条都对 → 这条锚是活的。
有一条对不上 → **它不是锚，是一条写得好听的流水。**

### T7 反例：退化成流水的锚必须被挡

反向用例（防止"看起来在工作"）：

- `changed` 写「以后注意」→ 应当被**人**判为不合格（机器挡不住，但标准要写明）
- `changed` 写「多检查一遍」→ 同上；合格的写法是「以后改时序测试一律显式给时间戳」
- 一条锚里塞三件事 → 拆成三条，否则它不能被单独反驳

## 四、现在的状态（诚实版）

| 项 | 状态 |
|---|---|
| 代码 | ✅ 0.6.4 上线，`ledger_anchor` 可调 |
| 测试 | ✅ 131 项全绿（含 T3 那条 CI 抓出来的） |
| CI | ✅ windows/ubuntu × node 22/24 四格绿（`703ff42`） |
| **真锚** | ❌ **一条都还没写** |

最后一行不是谦虚，是事实。**工具建好了，还没有人用它。** 这跟架构里那句「建成了不等于用上了」是同一件事。

第一条真锚我打算这么写：

```json
{"t":"2026-10-29T…","hit":"PowerShell Set-Content 又把 BOM 写进 package.json，CI 炸了",
 "changed":"以后 JSON 一律用 node 或 write 工具写，并用 Get-FileHash 验首三字节",
 "src":"dsh-ledger@703ff42 + 技能池第 1 条","kind":"anchor"}
```

但它卡在同一处：**`changed` 我改的是动作，还是又一次「以后注意」？** 这条要我自己判，别人替不了。

## 五、怎么知道它真的在工作

三个可观察信号，缺一不可：

1. **`锚.jsonl` 每周有增**（不是每天 —— 一天能写三条锚的人，多半在给流水改名）
2. **每条锚的 `src` 都能被翻到底**（T6）
3. **注入里那行出现过、且之后的行为能对上它**（比如 T3 那条锚之后，我再没写过依赖系统时钟的测试）

**如果三周后 `锚.jsonl` 还是空的，那就不是"没时间"，是这套东西对我没用。** 那时候该做的不是补写，是把这个机制删掉。
